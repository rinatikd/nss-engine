# Один процесс для UI и MCP

`web_app.py` и `mcp_bridge.py`, запущенные отдельно, используют одну SQLite, но владеют разными worker. Для совместной работы браузерного интерфейса и ChatGPT используйте единый процесс:

```sh
python unified_runtime.py --db /absolute/path/interface.sqlite --ui-port 8765 --transport stdio
```

MCP-stdio предназначен клиенту/туннелю, запускающему эту команду. Диагностика адреса UI идёт в stderr; stdout остаётся исключительно MCP-протоколом. Откройте `http://127.0.0.1:8765` на той же машине. Отдельный `web_app.py` для этой БД запускать не нужно.

Для локального MCP HTTP:

```sh
python unified_runtime.py --db /absolute/path/interface.sqlite --ui-port 8765 --transport streamable-http --mcp-port 8766
```

UI и MCP слушают только loopback; `localhost` не является публичной ссылкой для другого аккаунта. Туннель, учётные данные и разрешённое приложение ChatGPT настраиваются отдельно.

Теперь worker, запущенный MCP, виден в UI и останавливается из UI. Worker, запущенный в UI, виден и останавливается через MCP. Изменение моделей и запуск остаются атомарными. UI сохраняет Host/Origin/CSRF-проверки; MCP продолжает выдавать результаты без исходного prompt/rubric/attempt payloads. Платные API отключены.

Процесс владеет единственным Application и закрывает оба интерфейса совместно. Остановка прекращает новые шаги; запрос модели, уже находящийся в работе, не считается отменённым. Несколько отдельных runtime над одной БД не образуют общий контроллер; используйте одного владельца.

Проверка: официальный MCP stdio client + настоящий HTTP UI, mock только локальной доступности/ожидания worker. Три теста проверяют двустороннее управление, сохранение CSRF, отказ несовпадающей БД и закрытие UI listener. Это не доказательство реального вызова из ChatGPT.
