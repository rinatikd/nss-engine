# Chrome Bridge — восстановление после перезагрузки Windows

**Статус на 14.11.2026: исходники в PR #110, локальная установка и реальный E2E НЕ проведены.**
Нельзя считать этот пакет работающим на Work PC только из-за коммита в GitHub.

## Цель

1. Восстановить необходимые соединения после входа пользователя в Windows без повторного поиска PID, портов, старых скриптов и секретов.
2. Сохранить простую панель Chrome Bridge с двумя кнопками **Подключить / Отключить**: при включённом автозапуске локальные серверы уже должны быть доступны до нажатия **Подключить**.
3. Если автозапуск не сработал, предложить отдельное однонажатное восстановление через ярлык **Восстановить Chrome Bridge**. В будущем можно добавить тот же вызов через Chrome Native Messaging, но только с фиксированной операцией и проверенной установкой хоста.
4. Не дублировать процессы, не завершать неизвестные PID, не трогать production и не сохранять секреты в скриптах.

## Реализованные компоненты

- `tools/ai_collaboration/recovery/Restore-LocalStack.ps1`: STATUS/RESTORE, фиксированные пути, сравнение процесса/порта, mutex, без остановки чужих процессов; запускает PR102 Lab, PowerShell Direct и PR102 Tunnel только если выполняются локальные предпосылки.
- `Recover-PowerShellDirect.ps1` и `Recover-LabTunnel.ps1`: восстановление известных профилей при отсутствии соответствующего процесса. Состояние `PROCESS_STARTED_REMOTE_HEALTH_NOT_VERIFIED` **не равно** готовности удалённого MCP.
- `Save-RecoveryCredential.ps1`: однократный локальный скрытый ввод Control Plane API key, хранение через Windows DPAPI текущего пользователя; нельзя загружать DPAPI-файл в GitHub/облако.
- `Recovery-Watchdog.ps1`: ровно одна попытка Restore после входа в Windows, затем ограниченные проверки исключительно в режиме Status; неопределённые результаты не перезапускаются; журнал только с состояниями.
- `Register-StackRecovery.ps1`: отдельно запрашиваемая регистрация non-admin Scheduled Task (текущий пользователь), при желании создание ярлыка на рабочем столе, вызывающего проверенный пакет и показывающего локальное окно с итогом.
- `Prepare-RecoveryRelease.ps1`: из чистого checkout создаёт отдельную копию release-скриптов, не перезаписывая существующую установку; SHA256 manifest (не цифровая подпись).
- `recovery-plan.mjs`, `recovery-runtime.mjs`, `recovery-journal.mjs` и тесты: дальнейшая основа унифицированного API управления, который потребует независимого review. Не подменять Python/PowerShell исполнитель JavaScript-планом без явного интеграционного этапа.

## Последовательность первоначальной установки — НЕ выполнять до тестов и согласованного GO

1. В отдельном чистом checkout платформенной ветки проверить все файлы, подписи/хеши, Windows-совместимость. Запустить `node --test tools/ai_collaboration/recovery/*.test.mjs` на Windows.
2. Провести read-only `Restore-LocalStack.ps1 -Mode Status` и `Register-StackRecovery.ps1 -Mode Check`. Сверить точные пути, PID, конфигурации, реальные службы.
3. Вручную один раз запустить `Save-RecoveryCredential.ps1` (скрытый ввод; НЕ присылать ключ в чат). Проверить DPAPI-доступ в контексте той же учётной записи. Ключ может потребовать переэнролла после смены Windows-профиля/переустановки.
4. Из чистых файлов создать `C:\Engineering\ChromeBridge-Recovery-Release`, сверить манифест, выполнить в режиме STATUS, затем локальный RESTORE на изолированном стенде с намеренно остановленным PR102 (не на production).
5. После принятия DENY/ALLOW/duplicate/occupied/unknown/recovery сценариев явно зарегистрировать задачу на вход в Windows и ярлык. Не включать выполнение от SYSTEM или с повышенными правами.
6. Проверить полный перезапуск тестового Windows-профиля/VM (или контролируемое воспроизведение logon) и затем фактический `browser_status` через ChatGPT. **Не перезагружать основной Work PC ради эксперимента**, пока весь рабочий стек не покрыт и нет отката.
7. Добавить остальные серверы/туннели только после точной инвентаризации их PID, скриптов, profiles, secrets, dependencies и safe-stop/rollback.

## Релизные критерии

- STATUS ничего не меняет; повтор RESTORE не создаёт дубли.
- Чужой PID, занятый/неизвестный порт и неподтверждённая принадлежность -> BLOCKED.
- Туннель запускается с ранее существующим профилем, без логирования секрета; в выводе **отдельно** указывается, что remote MCP не проверен.
- При отсутствии DPAPI ключа запускаются только независимые безопасные части; причина формулируется без секрета.
- Task Scheduler не устанавливается автоматически при клонировании; включается отдельной командой; возможно отключение и удаление.
- Никаких изменений production 17381/17382, существующих туннелей и текущей конфигурации PR113 без отдельной приёмки.
- После успешного автостарта достаточно открыть Chrome и нажать **Подключить**. Если backend не восстановился — ярлык ручного восстановления в одно действие.

## Уточнение реализации по результатам аудита (14.11.2026)

- Запуск повторных `Restore` на основе одного лишь `START_UNCONFIRMED` устранён. Это опасно при потере подтверждения запуска туннеля: новая попытка могла бы создать дубликат. Только первый проход может создавать процессы, следующие проходят в режиме `Status`.
- Для существующего PowerShell Direct и уже работающего PR102 tunnel выводим отдельное состояние `ALREADY_..._REMOTE_HEALTH_UNVERIFIED`, а не ошибочное `BLOCKED`. Это **не** означает успешной авторизации ChatGPT — необходим отдельный реальный MCP probe.
- Ярлык `Восстановить Chrome Bridge` вызывает `Restore-StackWithReport.ps1` (через проверенный `Invoke-VerifiedRecovery.ps1`) и показывает локальное окно с итогом. Scheduled Task не использует интерактивный интерфейс.
- Добавлены `windows-recovery-contract.test.mjs` как статические проверки Windows скриптов. Они не заменяют исполнения PowerShell/DPAPI/Task Scheduler на Windows.
- Установка Recovery и Chrome Native Messaging пока **не выполнялись**. Автозапуск привязан ко входу пользователя в Windows, а не к раннему старту ОС до входа; это соответствует выбранному хранению DPAPI текущего пользователя.

## Новая интеграция с панелью Chrome Bridge PR113

- В ветке PR113 добавлена отдельная кнопка **«Восстановить службы Windows»**; в manifest разрешено `nativeMessaging`.
- Расширение отправляет только `{"action":"restore"}` локальному Chrome Native Messaging Host `com.chrome_bridge.recovery`; не передаёт команду PowerShell, путь, токен, внешний URL или текст запроса.
- Самостоятельный .NET 8 helper `tools/ai_collaboration/recovery/native-host/Program.cs` запускает проверенный entrypoint из фиксированного каталога и возвращает ограниченные статусы. Запускается самим Chrome и не зависит от `127.0.0.1:17484`.
- Первоначальная установка требует локальной регистрации Native Messaging Host в HKCU, а также привязки **конкретного extension ID** `ehmllfabjbfcinaigionjggbgonkokfg`. Если при новом пути unpacked-расширения изменится ID, потребуется отдельно проверить новый ID и обновить регистрационный манифест. Старое расширение нельзя бездумно удалять.
- `Install-RecoveryNativeHost.ps1` выполняет `Check/Install/Uninstall`, создаёт self-contained Windows `.exe`, UTF-8 без BOM манифест для Chrome, не перезаписывает существующую запись.
- `Setup-Recovery.ps1` выполняет `Check/Install/Uninstall` для всего комплекта. В режиме Install сначала запускает Node tests, затем создаёт отдельный release, проверяет его, запускает STATUS, по необходимости предлагает скрыто зашифровать ключ через DPAPI, регистрирует Native Messaging Host и user-logon Scheduled Task/ярлык.
- Все действия Install изменяют локальную Windows-конфигурацию и поэтому требуют отдельного локального запуска/подтверждения после проверки. Наличие исходников в GitHub не означает, что эти действия уже произошли.
- Дополнительные тесты PR113: `docs/chrome-bridge-handoff/chrome-bridge-v20/tests/recovery-native.test.mjs`. Дополнительные тесты платформы: `native-host-contract.test.mjs`.

**Порядок E2E:** сборка + установка на изолированной копии Windows, Chrome reload под проверенным ID, кнопка на уже работающем стеке (ноль новых PID), DENY/отсутствие host, контролируемо остановленная PR102 Lab (полное восстановление сервера и туннеля), реальная проверка через ChatGPT, затем тест входа в Windows и удаления Scheduled Task. Рабочий ПК не перезагружать до разрешённого теста.

**Остаточный блокер на 14.11.2026:** действующий инструмент PowerShell Direct допускает лишь фиксированные read-only диагностики, а не запуск `Setup-Recovery.ps1` или `dotnet publish`. Автономно развернуть бинарный native host и запись HKCU через текущий чат невозможно; требуется сначала однократное локальное внедрение доверенного исполнителя или запуск установщика на Windows. Не обходить эту границу с помощью браузерного JavaScript.
