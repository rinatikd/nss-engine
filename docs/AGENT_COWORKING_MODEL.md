# Рабочий цикл совместной работы ИИ-агентов

Этот документ задаёт единый порядок от выбора задачи до интеграции. Он автоматизирует учёт и повторение цикла через GitHub Issue и PR; сам факт публикации Issue не отправляет сообщение внешнему ИИ и не подтверждает, что он получил задание.

## Принципы маршрутизации

- На одну задачу назначается один исполнитель и отдельный проверяющий. Исполнитель выбирается по подтверждённому каналу, доступному контексту, подходящим инструментам и результатам предыдущих задач.
- До назначения координатор проверяет очередь и открытые ветки/PR. Фиксируются Task ID, исполнитель, проверяющий, базовая ветка и полный SHA, разрешённые пути, критерии, зависимости, конфликтующие задачи и контрольная точка.
- Issue — спецификация, не передача. Статус `sent` допускается только после фактической отправки через указанный канал; к записи прикладываются ссылка/идентификатор передачи и точное задание. Если канала нет, статус `blocked-channel`, исполнитель не считается назначенным.
- Не передавать внешнему сервису закрытые чертежи, секреты, токены и другие проекты. Передавать только минимальный публичный контекст задачи.
- Один и тот же файл не назначается двум исполнителям одновременно. При пересечении сначала заканчивается или явно закрывается первое назначение; чужую ветку не перезаписывать.

## Состояния и доказательства перехода

| Статус | Значение | Необходимое свидетельство |
|---|---|---|
| `proposed` | Идея зафиксирована, спецификация ещё проверяется | Issue с целью; пробелы и вопросы перечислены |
| `ready` | Задание достаточно ограничено для передачи | Issue содержит SHA, файлы, критерии, зависимости, проверяющего и контрольную точку |
| `sent` | Точный пакет передан исполнителю | Канал и ссылка/идентификатор реальной отправки, дата, версия задания |
| `acknowledged` | Исполнитель подтвердил получение и понял границы | Ответ исполнителя; одного статуса доставки недостаточно |
| `in-progress` | Исполнитель работает | Ветка/среда и последний известный SHA или короткий checkpoint |
| `response-received` | Получен PR или отчёт | Ссылка, commit SHA, перечень изменённых файлов и заявленные проверки |
| `review` | Проверяющий независимо оценивает результат | Проверка diff, критериев, доказательств, конфликтов и необходимых тестов |
| `changes-requested` | Найдены исправимые замечания | Каждый пункт с путём/местом, условием, ожидаемым/фактическим поведением и проверкой |
| `rework-in-progress` | Исполнитель устраняет замечания | Точная передача ему списка замечаний и подтверждение |
| `rework-received` | Исполнитель ответил на замечания | Ответ на каждый пункт, новый SHA и повторные результаты |
| `verified` | Проверяющий подтвердил критерии | Отдельный проверяемый отчёт; открытые ограничения перечислены |
| `integrated` | Принятое изменение включено в main | Фактический merge commit/SHA и зелёные обязательные проверки |
| `blocked` | Нельзя продолжать без внешнего условия | Конкретный блокер, его источник, что уже проверено и условие снятия |

Статусы описывают факты, не намерения. В частности, Issue создана ≠ `sent`; ответ агента ≠ `verified`; PR открыт ≠ интегрирован; закрытый Issue ≠ доказательство merge.

## Передача и повторная итерация

1. Координатор публикует Issue после проверки пересечений, затем отправляет тот же текст задачи по реально подключённому каналу.
2. Исполнитель подтверждает получение и возвращает работу отдельным PR/отчётом. Каждая проверка привязана к точному SHA.
3. Проверяющий сопоставляет изменения с Issue и пишет замечания как воспроизводимые пункты, а не общие оценки. Если замечаний нет, статус `verified`; иначе `changes-requested`.
4. Координатор возвращает замечания тому же исполнителю в том же Issue и просит продолжить его ветку/PR, если база и границы не изменились. Не создаётся параллельная конкурирующая правка.
5. При каждой итерации исполнитель отвечает по пунктам и приводит новый SHA и фактические команды. Проверяющий заново проверяет все затронутые критерии и регрессии.
6. Если изменились цель, базовая SHA, разрешённые файлы или инженерные входы, координатор фиксирует изменение спецификации и заново оценивает зависимости до продолжения.
7. После проверки координатор разрешает интеграцию по правилам репозитория. Слияние выполняет владелец/уполномоченный интегратор; автоматическое слияние не включается.

## Пакет задания и отчёт

Issue должна содержать: Task ID; исполнителя; проверяющего; цель; основу (ветка + полный SHA); только разрешённые пути; критерии приёмки; зависимости/пересечения; входные данные; запреты; команды проверки; контрольную точку и следующий шаг.

В каждом ответе исполнителя: исходная SHA; файлы; точные места замечаний; условие воспроизведения; ожидаемое и наблюдаемое поведение; влияние; минимальное изменение; проверки, фактически выполненные и пропущенные; новая SHA или причина отсутствия патча. Не выдавать концептуальный diff за готовую правку и автономные тесты за проверку в AutoCAD/Revit.

## Доступность каналов

Координатор ведёт подтверждения по каждому конкретному инструменту/сессии. Упоминание поставщика в форме или исторический успешный запуск не означает, что канал активен сейчас. Перед отправкой проверяются фактическое наличие инструмента, вход в аккаунт, права, допустимый объём контекста и стоимость. Платный путь, новый секрет/доступ или платные ресурсы не включаются без отдельного согласия владельца.

Если канал недоступен, сохранить задачу в `ready` или `blocked`, записать проверенный блокер и выполнять независимую работу. Не писать `sent`, не симулировать ответ и не использовать пользователя как штатного переносчика сообщений, когда можно обратиться по подключённому каналу.

## Проверка результата и ежедневная координация

- Для кода проверяющий использует актуальные проектные инструкции, проверяет узкий diff, repo_guard и переносимые проверки. Нативную Autodesk-проверку отмечает отдельно.
- Для инженерного анализа исходные данные и применимые нормы должны иметь установленные источники; недостающие данные не додумываются.
- Ежедневно координатор просматривает текущие задачи, актуальность блокеров, конфликты файлов, полезность каналов и выполненные проверки. Если в очереди уже есть отчёт за день, обновляет его вместо дубликата.
- Сводный проектный вывод строится только из результатов со статусом `verified`, а внедрённое решение — из `integrated`. Открытые замечания и неопределённость остаются видны.

## Известная граница автоматизации

GitHub формы, Issue, PR и шаблоны делают пакет задания и журнал итераций повторяемыми. В текущей рабочей среде нет универсального подключённого dispatch-интерфейса к Claude, Grok, Gemini, DeepSeek и Qwen; создание Issue не может само запускать этих поставщиков. Не добавлять Action, требующий внешнего API-ключа, и не заявлять автоматическую отправку, пока конкретный бесплатный/разрешённый канал не проверен. При появлении канала включать его отдельным узким изменением с подтверждением прав, политик хранения и фактического результата.
