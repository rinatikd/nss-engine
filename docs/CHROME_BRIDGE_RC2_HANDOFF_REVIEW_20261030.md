## Что исправлено в рабочей ветке

В полученной изолированной сборке `extension/control.js` настроен на 17384,
а канонические исходники используют 17381. Сам сервер сохраняет стандартный
порт 17381; изолированные launcher задают 17384 переменной окружения.

Исправление фикстуры из handoff правильно для этого пакета, но его жёсткая
привязка к 17384 ломает каноническую сборку. В рабочей ветке фикстура теперь
находит ровно одно объявление loopback `BRIDGE`, проверяет допустимость порта
и направляет временную копию расширения на свой тестовый сервер. Выбор
`CHROME_BRIDGE_E2E_CHANNEL=msedge` перенесён; по умолчанию остаётся Chromium.
Runtime сервера и расширения не менялся.

Добавлены две регрессионные проверки к тестам сборщика: порты 17381/17383/17384
с LF/CRLF и отказ при отсутствующем, неоднозначном или недопустимом адресе.
Проверки исполняют настоящий блок настройки E2E в изолированных временных файлах.
Набор сборщика и установщика: 40 тестов, 34 PASS, 6 Windows-only SKIP, 0 FAIL.
Инвентарь и SHA-256: 37 overlay и 39 baseline файлов, синтаксис 52 JS-файлов.

Unicode escapes строки `До окончания:` в handoff корректны: проверено
вычислением JS-литерала. В оригинальном файле UTF-8 также содержит корректную
кириллицу. Это не найденная ошибка runtime расширения.

## Chrome 146: следующий локальный этап

Неудача `--load-extension` подтверждает проблему автоматической загрузки этим
способом, но не доказывает несовместимость расширения с обычной ручной загрузкой.
Проба `RC2-chrome-extension-probe.mjs` не включает Developer mode и проверяет
число элементов Load unpacked вместо их видимости. Поэтому тайм-аут клика
также не доказывает отказ штатной загрузки.

Локальному Codex CLI:

1. Использовать уже распакованный `ChromeBridge-RC2-Windows-Validation/candidate`.
   Не пересоздавать handoff и не подменять действующую RC1 на 17383.
2. Исправления проверять в новой рабочей копии; оригиналы и манифест handoff
   оставить неизменными. При правке PowerShell проверить AST в Windows 5.1.
3. Для Chrome создать отдельный пустой профиль и открыть `chrome://extensions`.
   Включить обычный Developer mode, проверить видимость и доступность
   Load unpacked, загрузить `candidate/extension` штатным способом.
   Не менять политики браузера и пользовательский рабочий профиль.
4. Зафиксировать реальный ID нового расширения. Не переносить в него pin RC1:
   ID распакованного расширения зависит от каталога. Если стандартная загрузка
   недоступна, записать точную причину и не выдавать Chromium/Edge за Chrome.
5. Для изолированной сборки использовать `Setup-RC2-Isolated.ps1 -ExtensionId <ID>`
   и `Start-RC2-Isolated.ps1`: отдельное состояние, порт 17384, без изменения MCP.
   Browser token переносить только локально в интерфейс расширения.
6. Подтвердить подключение и чтение состояния без отправки сообщения.
   Проверку реального обмена проводить отдельно в безвредной тестовой беседе,
   после локального Grant control; один requestId, без автоматической переотправки.
7. Не повторять пройденные native CLI/Claude проверки RC1 как будто это RC2.
   Новый результат записывать с точной версией, браузером и проверенными сценариями.

Сопутствующие неточности полученного пакета: `RELEASE_CANDIDATE_RU.md` всё ещё
указывает RC1 state/17381; для изолированного пакета следовать его специальным
launcher. `Test-RC2-Windows-ReadOnly.ps1` наблюдает 17383/17381, но не 17384;
добавить 17384 в рабочей копии. Он также рекурсивно проверяет JS внутри
`node_modules`, если зависимости установлены: ограничить синтаксическую проверку
поставленными исходниками. Статические metadata и внутренний манифест кандидата
после изменения E2E не являются повторной аттестацией его состояния.

Результат: исходный handoff целостен; переносимый дефект фикстуры исправлен.
Финальный выпуск RC2 на Windows и штатная загрузка в Chrome остаются
отдельными незавершёнными проверками. Платных API-вызовов не было.
