# Канал обмена агентов через GitHub (CHANNEL-01)

Задача: Issue #23. Мост `tools/agent_bridge/bridge.py` связывает комментарии GitHub Issue с локальными `codex exec` и `claude -p` на ПК владельца. Только стандартная библиотека Python и `gh`. Без GitHub Actions, без платного API, без сервера.

> **Репозиторий `rinatikd/nss-engine` публичный.** Всё, что агент напишет в ответе, мост публикует комментарием, и это видят все. Очистка секретов работает по шаблонам и не гарантирует, что в ответ не попадут пути, имена, фрагменты чертежей или закрытых данных. Не адресуйте агенту задачи, ответ на которые нельзя публиковать.

**По умолчанию мост ничего не меняет.** Без `--live` он только читает Issue и печатает, что сделал бы: не запускает агентов, не публикует комментарии, не пишет состояние.

## Формат сообщения

Первая строка комментария — скрытый заголовок, дальше текст по `docs/CLAUDE_HANDOFF_TEMPLATE.md`:

```
<!-- nss-agent-msg v1 id=<id> from=<отправитель> to=<получатель> re=<id родителя или -> hop=<0..3> mode=<review|analysis|status|rework|...> -->
Статус: ACCEPTED | NEEDS_INFO | REPORT | BLOCKED
Task ID: ...
База: <branch @ full SHA>
...
```

- Участники: `owner`, `codex`, `claude`, `gemini`, `grok`, `deepseek`, `qwen`. Запускать мост умеет только `codex` и `claude`.
- Заголовок учитывается, только если он стоит в самом начале комментария. Цитата или блок кода с заголовком в середине текста игнорируется.
- `id`: латиница, цифры, `.`, `_`, `-`, до 80 символов. Повторный `id` в той же Issue недействителен: учитывается самый ранний комментарий.
- Ответ: `re=<id исходного>`, `hop` на 1 больше. Мост добавляет к своим ответам `via=bridge` (это пометка, не доказательство).

## Команды

```
python tools/agent_bridge/bridge.py poll  --agent codex --issue 23            # пробный режим
python tools/agent_bridge/bridge.py poll  --agent codex --issue 23 --live     # один проход, реальный запуск
python tools/agent_bridge/bridge.py poll  --agent claude --issue 23 --live --watch --interval 120
python tools/agent_bridge/bridge.py inbox --agent claude --issue 23
python tools/agent_bridge/bridge.py send  --issue 23 --from owner --to codex --mode review --body-file task.md [--live]
python tools/agent_bridge/bridge.py wait  --issue 23 --re <id> [--from codex] --timeout 600
```

Общие параметры: `--repo` (по умолчанию `rinatikd/nss-engine`), `--owner` (по умолчанию владелец репозитория), `--state-dir`, `--max-hop` (только уменьшить, максимум 3).

- `poll` — находит сообщения `to=<agent>`, проверяет их и с `--live` запускает агента. Ответ публикуется в той же Issue с `re=` и `hop+1`. Без `--watch` выполняется один проход; с `--watch` повторяется до Ctrl+C (интервал не меньше 30 с).
- `inbox` — только чтение: сообщения агенту, ещё не обработанные мостом, и решение моста по каждому.
- `send` — собирает правильный заголовок и вычисляет `hop` по цепочке `re`. Без `--live` только печатает текст.
- `wait` — только чтение: ждёт комментарий с `re=<id>`; код выхода 3, если ответа нет за `--timeout`.

## Защитные правила

| Правило | Как реализовано |
|---|---|
| Пробный режим по умолчанию | Без `--live` нет запуска агента, `POST` в GitHub и записи состояния. |
| Только сообщения владельца | Автор комментария = `--owner` **и** `author_association=OWNER` **и** в заголовке `from=owner`. Сообщения агентов (`from=codex` и т. д.) по умолчанию отклоняются (`sender-not-owner`); цепочку агент → агент включает только `--allow-agent-chain`. |
| Лимит цепочки hop=3 | `hop` пересчитывается мостом по цепочке `re` и берётся максимум из заявленного и вычисленного. Подделка `hop=0` не сбрасывает счётчик. Обрыв цепочки (неизвестный или более поздний родитель) — отказ. При `hop>=3` агент не запускается; `send` отказывается публиковать `hop>3`. |
| Один запуск на агента | Каждый комментарий запускается не более одного раза: отметка `started` сохраняется **до** запуска, поэтому сбой не вызовет повтор. Замок `<state>/<agent>.lock` не даёт запустить двух одинаковых агентов одновременно, даже из разных окон. За один проход — не больше `--max-runs` (по умолчанию 1) запусков. |
| История не исполняется | При первом `--live` проходе по Issue запоминается последний существующий комментарий (baseline); выполняются только более новые. `--include-backlog` отключает это. |
| Тайм-аут | `--timeout` (по умолчанию 900 с). По истечении дерево процессов агента убивается (`taskkill /T /F` в Windows), в Issue публикуется `Статус: BLOCKED` без вывода агента. |
| Только чтение для агента | `codex exec --sandbox read-only --ephemeral`, `claude -p --permission-mode dontAsk --tools Read,Grep,Glob --no-session-persistence`. Запрос передаётся через stdin, не в командной строке. Текст сообщения помечен в запросе как данные отправителя. |

## Секреты и журналы

- Агент получает **разрешённый список** переменных окружения (PATH, профиль, TEMP, `CODEX_HOME`, `CLAUDE_CONFIG_DIR` и т. п.). `GH_TOKEN`, `GITHUB_TOKEN`, `*_API_KEY` и другие не передаются: агент не может писать в GitHub токеном моста и случайно перейти на платный API-ключ. Дополнительную переменную можно передать только явно: `--pass-env NAME`.
- Перед публикацией вывод агента очищается: шаблоны токенов GitHub, `sk-…`, AWS, Slack, Google, JWT, приватных ключей, `Authorization/Bearer`, значения переменных окружения с секретными именами, путь домашнего каталога → `~`. `@упоминания` обезвреживаются, чтобы ответ агента никого не уведомлял. Ответ обрезается до 60 000 символов.
- Состояние и журнал хранятся **вне репозитория**: `%LOCALAPPDATA%\nss_agent_bridge\` (или `~/.local/state/nss_agent_bridge/`, или `NSS_BRIDGE_STATE_DIR`). В журнал пишутся только метаданные: номер комментария, id, from/to, hop, решение, код выхода, длительность и длины вывода. Тексты сообщений и вывод агента в журнал не попадают; stderr агента не сохраняется и не публикуется.
- Тело комментария передаётся в `gh api --input -` через stdin. Ошибки `gh` тоже проходят очистку.

## Изоляция чтения: проверка 2026-11-01

Агента запускали ровно как мост: та же команда, разрешённый список переменных окружения, рабочая папка = корень репозитория. GitHub при этом не использовался. Агента просили прочитать файл вне репозитория в домашнем каталоге и вернуть только признак «читается или нет».

| Агент | Результат |
|---|---|
| `claude` (Claude Code 2.1.316, `-p --permission-mode dontAsk --tools Read,Grep,Glob`) | **Не читается.** Ни `~/.claude.json`, ни пробный файл со случайной меткой в домашнем каталоге не прочитаны: метку агент не вернул. Вероятная причина — чтение вне рабочей папки требует разрешения, а `dontAsk` его не даёт; это вывод по поведению, не по исходникам. |
| `codex` (codex-cli 0.166.0, `exec --sandbox read-only`) | **Не проверено.** Аккаунт Codex исчерпал лимит до 2026-11-27; запуск дошёл до сервиса и остановился с ошибкой лимита. Режим `read-only` по своему описанию запрещает запись, а не чтение. Пока нет проверки, считайте, что Codex может прочитать любой файл, доступный пользователю, и не запускайте `poll --agent codex --live`. |

Проверку на `~/.claude.json` для Codex заблокировал классификатор безопасности Claude Code: содержимое ушло бы стороннему сервису. Для Codex используйте пробный файл без секретов со случайной меткой: если агент вернул метку, значит, он читает вне репозитория.

Переменные профиля (`USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `HOME` и т. п.) оставлены в разрешённом списке. Без них `claude -p` не авторизуется («Not logged in»), а `codex exec` авторизуется. Убирать их бесполезно: это не барьер для файловой системы, агент может прочитать файл по абсолютному пути. Ограничивает чтение только режим самого агента.

## Перед первым `--live`

- `gh` должен поддерживать `gh api --paginate --slurp`; проверено на gh 2.103.2. Если `--slurp` не распознаётся, обновите `gh`.
- Мост ищет `codex` и `claude` через `shutil.which`, поэтому в Windows подходят `codex.exe`, `codex.cmd` и `claude.exe`. На этом ПК 2026-11-01 найдены `codex.EXE` и `claude.EXE`; `claude` запущен из моста локально (без GitHub) и ответил. После обновления CLI или переноса на другой ПК повторите проверку изоляции чтения выше.
- Отклонённые сообщения посторонних авторов записываются в файл состояния, чтобы не обрабатывать их на каждом проходе. Файл растёт не больше числа комментариев в Issue; для сброса удалите его (см. ниже).

## Важное ограничение: «владелец» — это аккаунт, а не человек

**Проверка владельца подтверждает аккаунт, а не человека.** Ответы Claude Web, коннекторов и самого моста публикуются под тем же аккаунтом `rinatikd`. Поэтому проверка автора подтверждает только аккаунт GitHub. От автоматической петли защищают два других механизма: заголовок `from=owner` (по умолчанию мост реагирует только на него) и пересчитанный лимит `hop`. Агент, запущенный мостом, не имеет токена GitHub, а мост публикует его ответ только с `from=<agent>`. Но любой инструмент с токеном владельца может опубликовать `from=owner`, поэтому не подключайте к этому аккаунту автоматические сервисы, которые сами пишут комментарии.

## Включение и выключение

1. Проверить `gh auth status` и вход в `codex` и `claude` на ПК владельца.
2. Посмотреть пробный проход: `poll --agent codex --issue <N>`.
3. Включить: `poll --agent codex --issue <N> --live --watch` в отдельном окне (для Claude — отдельное окно с `--agent claude`).
4. Выключить: Ctrl+C в окне моста. Повисший замок старше `timeout+120` с снимается автоматически; при необходимости удалите `<state>/<agent>.lock` вручную, когда мост остановлен.
5. Сбросить состояние Issue: удалить `<state>/state-<repo>-<N>.json` (после этого снова будет установлен baseline).

Переопределить команды (для отладки и тестов) можно JSON-списком в `NSS_BRIDGE_GH` и `NSS_BRIDGE_CMD_CODEX` / `NSS_BRIDGE_CMD_CLAUDE`; `{output_file}` в команде заменяется путём файла с последним ответом агента.
